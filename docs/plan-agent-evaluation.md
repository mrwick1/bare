# Reproducible browser task evaluation

Plan destination in the child PR: `docs/plan-agent-evaluation.md`.

## Why
Tool correctness does not prove that agents complete tasks. Add reproducible tasks, independent success checks and transcript scoring so we can measure completion and accidental repeat actions alongside calls, response size, CPU and memory. Do not label a scripted runner as a real model-agent evaluation.

## Current state and owned files
Existing tools/bench/journeys.py and journeys.sh measure recorded bare-drive journeys with instruction counts, CPU/wall time and RSS. Read and reuse their approach where it fits, but do not modify those benchmark semantics. Existing loopback fixtures live under tools/fixtures/drive and crates/drive/tests/common/mod.rs; use them as references. Own new files under tools/agent-eval/, tools/fixtures/agent-eval/ and docs/agent-evaluation.md plus docs/plan-agent-evaluation.md. New dedicated test files under tools/agent-eval/tests/ are in scope. No production MCP/driver/browser Rust changes, no guide/README edits and no new Python dependencies.

## Task and scoring contract
Use Python stdlib for a small JSONL MCP transcript collector/runner, deterministic loopback fixtures, and independent graders. Define at least these tasks: login/session restore; search/extraction; duplicate button disambiguation; an overlay followed by delayed submission result; navigation and stale-ref recovery; two independent sessions/tabs; upload; download. Fixtures must supply explicit reset/seed behavior and synthetic identities. A form-submit endpoint keeps an independent submit counter; a task fails if the agent submits more than once even if the final page says success. Grade results from fixture state/artifacts and expected content, not the agent's self-report or an 'ok' receipt. Extraction tasks must compare expected data, and upload/download tasks must compare exact bytes or a hash.

Record a manifest with task id/version, fixture seed, browser SHA/binary identity, runner identity, viewport, timeouts and run id. Collect tool calls and JSON-RPC results with request IDs, session identifiers, monotonic timestamps and encoded byte counts. Collect actual token usage only when supplied by the caller/harness; otherwise mark it unavailable, never estimate tokens from bytes and call that measured usage. Include completed task count, failed assertions, duplicate submissions, tool call count, response bytes, elapsed time, process CPU and peak RSS where available. Capture only owned process resources and distinguish process-wide from per-task totals. Missing perf or platform counters are null with a reason, never zero. Protect transcript values using synthetic data and explicit exclusion/redaction of authentication state; no credential or token dumps.

Provide two modes: deterministic protocol smoke runs with a supplied sequence, and scoring/collection of an externally supplied real-agent transcript against the same task fixtures. A smoke run is labelled scripted. Do not add an LLM API client, model dependency, credential lookup or paid run. Actual model-agent results remain unverified unless a real current-harness run is performed and the prompt/model/tool setup is recorded. Do not fabricate a before/after model comparison. This PR should make later real-agent runs possible without changing fixture/scorer contracts.

## Implementation record

Starting SHA: `00e701b089a9abe9a399bbe69150c5d772b5c4cc` (same as the inspected main; no rebase needed). Results and commands: `docs/agent-evaluation.md`.

Deviations from the plan, with the reason:

- Peak RSS comes from `/proc/<pid>/status` `VmHWM`, not from `wait4`. A forked child shows its parent RSS in `ru_maxrss` (test: a `sleep` child showed 216944 KiB). The first smoke run showed this as an RSS that grew from task to task.
- A smoke run starts one `bare-mcp` process per task. This makes the process figure also the per-task figure. The summary says so.
- `fixture` and `score` are two separate commands for an external agent. `fixture` runs in the foreground until its deadline or a signal, then writes the fixture record. `score` needs that record, because the grader must read the fixture state and not the agent report.
- Python unit tests use a fake MCP server (`tests/fake_mcp.py`) for the collector (out-of-order replies, deadline) and for the check that a server that only says `ok` completes no task.
- No unsupported browser feature was found. The `nav_stale_ref` script includes one deliberate stale-ref call; the browser refused it as expected.
- No integration hunks: this branch changes no file outside its scope. It does not depend on PR #614. The scripts use `act` with `snapshot:false` and read no receipt field, so they should not depend on #614 fields. This was not tested against #614.
