# How V8 handles each part of the engine (reference)

This page is a reference for `design-engine-rewrite.md`. It lists how V8 solves each module of the plan, with the numbers that V8 published, and how the plan compares. It does not change the plan.

Sources read on 2026-11-18, all on <https://v8.dev/blog/>: `ignition-interpreter`, `sparkplug`, `maglev`, `pointer-compression`, `fast-properties`, `slack-tracking`, `elements-kinds`, `preparser`, `v8-lite`, `trash-talk`, `concurrent-marking`, `high-performance-cpp-gc`, `embedded-builtins`, `code-caching-for-devs`, `adaptor-frame`. Numbers are V8's, on V8's benchmarks. They are not measured on Bare.

## Parser and pre-parser

V8:

- The pre-parser checks the syntax of an inner function and builds no tree. The function is fully parsed and compiled at its first call.
- Since V8 6.3, the pre-parser resolves scopes fully. It stores the result as a dense array of flags per variable. A later full parse of the outer function reads the flags and skips the inner functions. Each function is "at most preparsed once, and fully parsed once".
- Before 6.3, inner functions were pre-parsed again at each nesting level, so the cost grew faster than linear with the depth.
- The flag data is only kept for functions that have inner functions. It is garbage after compile.
- Eager compile for "possibly invoked function expressions": `(function` and the `!function`, `,function` chains of UglifyJS. Eager compile of everything costs significant memory and slows load.

Plan: the same model (6.9 items 4 and 9, 6.10 item 10). Today's nested skip ranges (`parse.rs:3329`) already give "parse once". The V8 heuristic does not cover webpack module functions in an object literal, as the round 2 review noted.

## Interpreter and bytecode

V8 (Ignition):

- A register machine with an accumulator. Many bytecodes read and write the accumulator implicitly, so they carry fewer operands.
- Bytecode is 25% to 50% of the size of the baseline machine code it replaced. Ignition cut the memory of a Chrome tab by about 5% on low-memory Android.
- The bytecode generator removes some redundant operations and register moves as it emits code.
- The handlers are generated by the TurboFan back end from a portable macro-assembler, not written in C++ or in assembly.

Plan: 32-bit words with explicit register operands, no accumulator. An accumulator is an option that the plan does not compare (not measured: operand bytes per op and `Mov` count with an accumulator). The handlers are Rust match arms.

## Calls and frames

V8:

- An interpreter frame has fixed slots: return address, previous frame pointer, context, function, bytecode array, bytecode offset, and since V8 8.9 the actual argument count. The registers follow.
- Arguments are pushed in reverse order, so argument `i` is at a fixed offset from the frame pointer. A call with too few arguments pads with `undefined`. A call with too many leaves the extra ones on the stack.
- This removed the "arguments adaptor" frame. Gains: 11.2% on a call micro benchmark without the JIT, up to 40% with TurboFan, 7% on JSTests/Array.

Plan: one frame record on the JS stack (6.10 item 8) with a shared argument window (6.9 item 1). The same idea: no copy of the arguments.

## Baseline JIT

V8 (Sparkplug):

- It compiles from bytecode, with no intermediate form: "a switch statement inside a for loop". One prepass finds loops; V8 plans to remove it.
- Most of the code is calls to built-ins that match the interpreter's handlers.
- The frame is the interpreter's frame. The bytecode offset slot holds the feedback vector, and a table maps machine-code ranges to bytecode offsets.
- Tier switching between the interpreter and Sparkplug has almost no frame translation.
- Gains: 5% to 10% on Speedometer, about 5% to 15% of V8 main-thread time on browsing benchmarks.
- Maglev (the next tier) compiles about 10 times slower than Sparkplug and 10 times faster than TurboFan.

Plan: the same model (6.6 option A). The loop headers come from the compiler (6.11 item 19), as V8 plans. The feedback vector is reached from the frame (6.11 item 11), as in Sparkplug.

## Values

V8: a 32-bit tagged slot (pointer compression). It holds a 31-bit small integer or a 32-bit offset into a 4 GiB cage. Doubles are boxed. Tagged values were about 70% of the heap. Compression made the V8 heap up to 43% smaller and the renderer up to 20% smaller.

Plan: 64-bit NaN-boxing, no boxed doubles. Compressed pointers are open question 3 of the design.

## Objects and shapes

V8:

- The first field of every object points to its hidden class (map). The map holds the shape, the property count and the prototype.
- Objects that add the same keys in the same order share a map. Maps form a transition tree. Integer keys do not make new maps.
- The map points to a descriptor array: each key and where its value is stored.
- Properties are in the object (fastest) or in a separate property store that grows on its own (one more load).
- A plain object header is three words: map, property store, elements.
- After many adds and deletes, an object goes to dictionary mode. Inline caches do not work on dictionary properties.

Plan: the same map model, with a header of one word (6.4 option A) or a 32-bit shape id with flags (6.11 item 12). The property store and the elements pointer exist only in layouts that need them (6.9 item 5, 6.11 item 14). V8 always reserves both.

## Slack tracking

V8:

- A constructor's first objects get the expected property count plus 8 spare in-object slots.
- A counter on the initial map starts at 7. At the 7th construction, V8 shrinks the instance size to the most slots that any object of the map tree used.
- Unused slots hold a one-word filler, so the collector can step over the freed tail.
- Example from the post: an object with 2 properties goes from 13 words to 5 words (32-bit build).

Plan: inline slot count per allocation site from the observed shape (6.4 option A). Literals with fixed keys allocate their final shape (6.9 item 2), which needs no tracking.

## Arrays and elements

V8:

- Elements are stored apart from named properties. There are 21 elements kinds.
- Basic kinds: small integers, doubles, any value. Each has a packed and a holey form.
- Kinds form a lattice. An array only moves to a more general kind and never back. A holey array stays holey.
- A small-integer array needs no collector scan. A double array stores raw doubles.
- A packed array skips the hole check and the prototype lookup on each read.
- Large sparse arrays use a dictionary.

Plan: one tagged elements layout, dense or sparse, first (6.9 item 8). Typed kinds come only if an element census shows the work they remove.

## Inline caches and feedback

V8:

- Feedback (cache shapes, call counts) lives in a feedback vector per closure, not in the bytecode. The bytecode is shared.
- Since V8 7.x, the feedback vector is allocated only after the function has run about 1 KB of bytecode. Before that, a small `ClosureFeedbackCellArray` holds the closures it makes.
- Running with no feedback at all (an earlier Lite mode) cut page load time by 12% but raised V8 CPU time by 120%. Lazy feedback kept the CPU and saved the memory.

Plan: feedback on second use per site (6.9 item 7) in a per-realm feedback vector (6.11 item 11). V8 decides per function by bytecode run; the plan decides per site. S1 can compare the two.

## Heap, allocator and collector

V8 (Orinoco):

- Young generation: a semi-space copying collector (the scavenger). Half of the young space is always empty. An object that survives two collections moves to the old generation. Copy cost follows the number of survivors.
- A write barrier keeps a list of old-to-new pointers. With the stack and the globals, it is the scavenger's root set.
- Old generation: mark-sweep, with compaction only of fragmented pages. Free lists by size.
- Marking runs concurrently on helper threads. Two mark bits per object encode white, grey and black. A Dijkstra-style write barrier keeps "no black object points to a white object".
- The mark work list is made of segments. Each thread fills local segments and publishes full ones to a global pool.
- Concurrent marking cut main-thread marking time by 60% to 70%. The parallel scavenger cut main-thread young collection time by 20% to 50%. Idle-time collection cut Gmail's idle heap by 45%.

Plan: non-moving size-class blocks with lazy sweep first (6.10 item 15). A young generation only if journey survival data favor it (6.11 item 2). A work list that grows in chunks (6.11 item 3) is the single-thread form of V8's segments. No concurrent marking in the plan.

## Host interface and DOM

V8 and Blink (Oilpan, now `cppgc`):

- DOM objects are C++ objects in a garbage-collected heap. Each class has a `Trace` method that visits its pointers.
- V8 and Oilpan trace across the boundary "as one heap" (unified heap).
- `Member<T>` is a pointer inside the heap. `Persistent<T>` is a root from outside the heap.
- The stack is scanned conservatively: each word that looks like a heap pointer keeps its object alive. Blink tries to collect "when there is no interesting stack", which the event loop makes common.
- Sweeping runs on background threads. It cut main-thread sweep time by about 42% on average.

Plan: precise roots and collection between tasks (6.11 item 1). This is the same bet as Blink's "no interesting stack", without conservative scanning. Wrappers only on request, with tracing through nodes that have no wrapper (6.11 item 17).

## Built-ins and startup

V8:

- Built-ins are compiled at build time and embedded in the binary's read-only code section. All processes share them. Nothing is deserialized at startup.
- Compared with a startup snapshot loaded per isolate: median V8 heap 19% smaller, renderer 4% smaller, 1.9 MB saved per site at the median.
- The first version was more than 5% slower on Speedometer. Shorter call sequences brought it to about 0.5%.

Plan: lazy built-ins as today. Static realm recipes are low value on our journey (6.11): a realm costs about 70 K to 166 K instructions.

## Code cache

V8 and Chrome:

- An in-memory cache per isolate maps source text to bytecode. It has about an 80% hit rate in the field.
- The disk cache is attached to the HTTP cache entry. First run: compile. Second run: compile again, then store the code. Third run: load the code and skip the compile.
- The disk cache holds only the functions compiled when the script finished running. Scripts under 1 KiB are not cached. A changed URL or a 200 response starts again from cold.

Plan: code shared by all realms of a session, keyed by verified source identity (6.9 item 6). An optional disk cache is open question 6.

## Bytecode flushing and memory

V8:

- Bytecode and its metadata are typically about 15% of the heap.
- A function's age goes up at each major collection and goes back to zero when the function runs. Old bytecode is held weakly and flushed at the next collection, unless a stack frame uses it. The feedback vector is flushed one collection later.
- Source positions are made only when a stack trace needs them, by parsing again.
- Rare fields of a built-in object moved to a side table: only 3 of 11 fields were usually set.
- Together with lazy feedback: the V8 heap became 18% smaller on average (1.5 MB on AndroidGo) with no significant loss of speed.

Plan: flushing waits for a measured need (6.10 item 21). Lazy source positions and side tables for rare fields are not in the plan yet (not measured: the share of source positions in Bare's bytecode).

## Where the plan differs from V8 on purpose

- Non-moving heap. V8 moves young objects and compacts old pages. Moving objects in Rust needs precise rooting of every pointer; JavaScriptCore shows that a non-moving heap can be generational.
- One-word object header, against V8's three words.
- 64-bit NaN-boxed values, against 32-bit compressed slots with boxed doubles (open question 3).
- One thread. V8's concurrent marking, parallel scavenge and background sweep cut main-thread time but add total CPU. Our first priority is total instructions.
- No optimizing tier. Maglev and TurboFan come only after the baseline JIT is measured (6.6 option C).
