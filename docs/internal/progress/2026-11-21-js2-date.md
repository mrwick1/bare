# js2 Date (phase 2 of the fast plan)

js2 had no `Date`. 19 of 50 workloads call `Date.now` and 12 build dates. test262 Reflect tests failed on `Date.now`. This PR adds `Date` in Rust, in a new module, and makes `JSON.stringify` call `toJSON`.

## What is built

- `crates/js2/src/bi_date.rs`: the constructor (all forms, and `Date()` as a function), `Date.now`, `Date.parse`, `Date.UTC`, every getter and setter (local and UTC), `getYear` and `setYear`, `getTimezoneOffset`, `toISOString`, `toJSON`, `toString`, `toDateString`, `toTimeString`, `toUTCString` (`toGMTString` is the same function object), `valueOf`, `getTime`, `setTime`, `[Symbol.toPrimitive]`, `toLocaleString`, `toLocaleDateString` and `toLocaleTimeString`. `Object.prototype.toString` of a `Date` is `[object Date]` (one branch in `bi_object.rs`).
- The object is a plain `Object` cell with the flag bit 19 (`F_DATE`, defined in `bi_date.rs`) and the hidden slot `k_prim` that holds the time value, the shape of a wrapper (`bi_wrap.rs`). A class that extends `Date`, and `Reflect.construct(Date, [], F)`, take the prototype of `new.target`; a `prototype` that is not an object gives `Date.prototype`. A `Date` costs one 24-byte cell.
- Most methods are one native each whose slot 1 is an index into one table (`OPS`), and one `match` does the work. No new `unsafe`, no change to `Realm`, no change to a trait.
- `crates/js2/src/bi_date_calc.rs` and `bi_date_tz.rs` are copies of `crates/js/src/date.rs` and `tz.rs` of the old engine (the arithmetic, the parser with the legacy V8 formats, the TZif reader and the POSIX rule). js2 cannot depend on `bare-js`. The old engine goes away, so the copy is the one that stays. `bi_date_tz.rs` also holds the 13-zone table of long names for the text in parentheses of `toString` (from `tz_names.rs`). `bare-tzdata` is a new dependency of `bare-js2` (the embedded data; no change to `bare-tzdata`).
- The local zone is the same as in the old engine: `TZ` (a leading `:` is cut), else `bare_os::tz::local_zone()`, else UTC. It is read at the first local-time call, one per thread. No zone file of the system is read.
- `bi_json.rs`: `JSON.stringify` calls `toJSON(key)` of an object with `Realm::call_function` (it threw a `TypeError` that said the call was not built; the call is built). Without this, `JSON.stringify(new Date())` failed. The test that asserted the `TypeError` is now `json_stringify_calls_to_json_with_the_key`. `builtins.rs`: `ordinary_to_primitive` is `pub(crate)` and `install_date` is in the install list.

## Deviations from the old engine and from V8 (listed, not hidden)

- `toLocaleString`, `toLocaleDateString` and `toLocaleTimeString` write the `en-US` text in the local zone (`6/15/2020, 12:00:00 PM`, a plain space before `PM`, as the old engine prints a string) and ignore the locale and the options. js2 has no `Intl`. The old engine forwards to `Intl.DateTimeFormat`.
- `Date.now` and `new Date()` read the system clock. The old engine has `WallClock::Virtual` for tests. js2 has no virtual clock (it needs a `Realm` field, which is a core file).
- No cap on the number of dates or on the length of a date string, no step charge: js2 has no such limit machinery yet.
- The text in parentheses of `toString` is the long English name for 13 zones and `GMT+hh:mm` for any other (the old engine does the same; V8 writes the ICU name).

## Tests

| Command                                          | Result                                                                                                 |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| `cargo test --offline -p bare-js2 --lib bi_date` | 16 pass (11 `Date` tests over 51 scripts, each also run under constant collection, and 5 zone tests) |
| `cargo test --offline -p bare-js2 --lib`         | 594 pass, 0 fail                                                                                       |

The `Date` tests set the zone (`America/New_York`, `Asia/Kolkata`, `Asia/Kathmandu`, `UTC`, `+05:30`) and compare with Node 22. They cover the forms of the constructor, `UTC` and `parse`, all getters and setters, a gap and an overlap in New York, old dates (local mean time), invalid dates, the order of coercion, a setter whose argument changes the date, the brand checks, the property attributes, `toPrimitive`, subclasses and `Reflect.construct`.

**Differential run against the old engine** (`bare-js-diff`, one script of 230 printed lines: 23 parse strings, 13 time values with all getters and every text form, 13 constructor argument lists, 15 setters with 9 argument lists each on a valid and an invalid date, and error cases). The old and the new output are identical in `TZ` = `UTC`, `America/New_York`, `Asia/Kolkata` and `Australia/Sydney` (0 differing lines of 230 each).

**Startup (eager natives, as asked).** Each `Realm` makes the `Date` constructor, 3 statics and 47 methods. The setup rows grow by about 71,000 instructions: `interp_load loopfn 0` 998,608 to 1,069,584 (+7.1%), `script_run` of `var x = 1;` 2,080,248 to 2,157,444 (+77,196, +3.7%). The rows at the full N grow by the same 70,000 to 85,000 and by at most +0.03%. The lazy built-ins step 1 (`docs/design-js2-lazy-builtins.md`) removes this cost: the members of `Date` can wait for the first read of `Date`, as the members of `Symbol` do.

The old `date_load` example (`tools/js/date_load.sh`) is written against the API of the old engine and has no js2 form, so I used this script.
