# Cache API store (design-service-workers.md, step 6)

## Change

- `cache_store.rs` (new): the Cache API data of a session. Per origin it keeps the caches in creation order and the entries of each
  cache in insertion order. An entry is a GET request (URL with no fragment, and the request headers that the `Vary` of the
  response names) and a response (status, status text, headers, body as `Arc<[u8]>`, URL). It holds no heap object.
- The store lives in `WebStorage` behind `Arc<Mutex>`. A new tab, a dedicated worker on a thread (`IdbShare`) and a service worker
  of the session share it.
- The query follows "Query Cache" of the standard. A request that is not GET finds nothing unless `ignoreMethod`. `ignoreSearch`
  drops the query of both URLs. With no `ignoreVary`, each header that `Vary` names must be equal, and `Vary: *` never matches.
  `put` removes the entries that the new request matches, then adds the new entry at the end.
- `browser_caches.rs` (new): the native op `cs(op, ...)` of the shim. Headers cross as `name:value` lines.
- `shims/caches.js`: now an install function that takes `cs`. It keeps the API (`open`, `has`, `delete`, `keys`, `match` with
  `cacheName`; `match`, `matchAll`, `add`, `addAll`, `put`, `delete`, `keys` with the options). `put` reads the body (the response
  is used after it) and rejects with the messages of Chrome: a method other than GET, `Vary: *`, a used body, status 206, a scheme
  other than http(s).
- The profile keeps the store in `<profile>/caches.bin` (magic `barecs01`, same file rules as `sw.bin`). `StorageState::caches`
  carries it. An opaque origin ("null") is not kept.

## Cost when the page does not use `caches`

The shim is still made at the first read of `caches`, `CacheStorage` or `Cache`. A page that never reads them makes no object.
`WebStorage` holds one more `Arc` (an empty map). The `Saver` reads one more revision under a `Mutex` per tick.

## Tests

- `crates/bare/src/browser_caches_store_tests.rs` (new, 4 tests): a page and its service worker share the caches (`add` from the
  network, the response URL), the query options and `Vary`, the `put` rejections of Chrome, and the profile round trip (status and
  status text kept).
- Before the change, these tests do not build (`WebStorage::caches` and `StorageState::caches` do not exist), and the store was
  per realm and in memory only. After: 4 passed. `browser_caches_tests.rs` (2), `profile_tests`, `profile_permissions_tests`, the
  service worker tests and `browser_idb*` pass.

## Known deviations

- A cached response comes back as a new `Response`: `type` is "default", and the URL is an own property of the object. A status
  outside 200 to 599 (an opaque response) comes back as 200.
- `keys()` gives each request with the headers that `Vary` names, not all of its headers.
- `addAll` adds entry by entry; one failure does not undo the others.
- `caches` exists also in a page that is not a secure context (Chrome hides it there).
- The whole store is written again at each change (one file). A large cache costs a large write.

## Not tested

- A dedicated worker on a thread that uses `caches`.
- Windows.
