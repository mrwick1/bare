# js2 async functions (step A1 of `docs/design-js2-async.md`)

Stacked on [G3](2026-11-21-js2-iterators-g3.md) (#837, merged).

What is built.

- `async function`, async arrow and async method (class, object literal, static) compile and run. Async generators and `for await` are still not built (`unsup`).
- Three ops, all in the cold copy of the loop (`async_op` in `interp.rs`, `generator.rs`): `AsyncInit`, `Await`, `RetAsync`. `bytecode.rs` has the specs and `GK_ASYNC`.
  - `AsyncInit` is the first instruction. It makes the activation (an object with the flag `F_GEN` and five hidden slots; the fifth is the result promise) and the promise, and puts the activation in the frame record word of `new.target`. The function then runs in the frame of its caller until the first `await`.
  - `Await v` calls `PromiseResolve(v)` and `PerformPromiseThen` with the activation as the handler of both reactions and no derived promise. Then it saves the frame like `Yield` does (same save lists, `sent` and `mode` registers; the record is made at the first `await`) and returns the result promise to the caller.
  - `RetAsync v, c` resolves (`c` = 0) or rejects (`c` = 1) the promise and ends the activation. It is the only return of an async function.
- One catch-all handler covers all code after `AsyncInit` (the code at the end of the function too). It runs `RetAsync ex, 1`, so a throw in a parameter default or before the first `await` rejects the promise. `compile_async.rs` has the compile side.
- The resume is a job. `run_job` in `promise.rs` sees a reaction with no derived promise and an activation as handler, and calls `Realm::async_resume` (`reenter.rs`). That sends the value or the reason with `gen_request` and runs the frame on a pooled machine (`resume_raw`), like the top-level jobs. The result of that run is dropped. Only `STOP` is an error of the job; a frame that cannot be entered rejects the promise.
- `new.target` is `undefined` in an async function, `new` throws, and the function has no `prototype`. Its prototype is `%AsyncFunction.prototype%` with the tag `AsyncFunction` (made at the first closure). The `AsyncFunction` constructor is not built (it needs `Function` source text).
- `verify.rs` checks the async ops like the generator ops (the save list of `Await`, the kind of the code, no `Ret`).
- Annex B function hoisting out of a block now applies to plain functions only. An async function or a generator in a block is a block binding in sloppy code too (spec B.3.3). This fixed `switch/scope-lex-async-function` and was wrong for generators already.
- `promise_load` has three new rows: `await_prim`, `await_prom`, `async_noawait`.

## Tests

`compile_async_tests.rs`, 12 tests, each run plain and under constant collection: the first run is synchronous; return values; `await` of values, promises, thenables, rejections; a throw before the first `await` and in a parameter default; loops, `let` per iteration, `finally`, `for-of` across waits; `await` in every kind of expression and statement; methods, `this`, `arguments`, `super`; the job order against the spec; no `prototype`, no `new`; 50 functions in one queue; the Annex B rule. Three older tests that used an async function as the "not built" example now use an async generator.

`cargo test --locked -p bare-js2 --lib` (archMachine, debug): 622 pass, 0 fail. `cargo test --locked -p bare-js-api --features suite`: 32 + 112 + 1 + 5 pass.
